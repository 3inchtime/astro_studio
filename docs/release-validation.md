# Windows 发布验收

`Build Desktop` 在 PR、main 和 tag 上运行 Windows/macOS 的前端测试、生产构建、Rust 测试、格式与 Clippy。tag 构建必须提供 updater 私钥，显式生成签名附件与 `latest.json`；正常本地构建不要求签名。

发布先创建草稿，再下载 GitHub 上的实际附件验证：版本等于 tag、清单指向本仓库该 tag 的 NSIS 安装包、清单签名等于 `.sig` 附件，以及安装包内容和可信注释的 Ed25519/minisign 签名均通过应用内公钥校验。校验失败保持草稿，不修改已公开版本。

## 原生 Windows 验收（发布必需）

在隔离的 Windows 用户/虚拟机中执行，不能使用日常资料库。保存系统版本、旧版版本、测试时间、安装包 SHA-256、步骤和截图/日志到一个可访问的 HTTPS 证据链接。

1. 全新安装：启动签名 NSIS 安装包，检查启动、素材显示、系统文件选择器和退出。
2. 升级：安装上一个公开版本，在其中创建项目、图片、画布和测试配置；记录内容数量与图片哈希。安装本次 NSIS 包，确认数据及配置存在且凭据迁移没有显示明文。另用受控更新端点提供本次验证过的清单，验证应用内下载、验签与安装。草稿附件不对普通用户公开，测试端点应提供同一份安装包及签名，不能关闭客户端验签。
3. 画布：编辑后立即关闭、退出以及重启；重新打开最后内容。模拟保存失败时关闭被阻止，可以重试。移动导入图片原文件后画布仍可用；引用中的生成图不能被永久删除或自动清理。
4. 备份与恢复：创建可移植备份，预览、恢复并自动重启；核对图片、画布和数量，配置需重新输入凭据。回滚后原库仍可用。退出/重启前未保存画布必须被处理。
5. 升级失败：损坏签名或安装包必须被拒绝；网络失败可重试，不丢资料库。

所有步骤通过后，从 `release-verification` 构建附件取安装包哈希，并与实际测试文件的 `Get-FileHash -Algorithm SHA256` 比较。运行 `Publish Validated Release`，填写 tag、确切哈希、证据链接，并勾选已通过全部原生验收。

发布工作流再次对 tag 的确切 commit 运行完整双平台质量检查、重新下载附件并验证签名与哈希；随后将验收链接和哈希追加到 Release 说明并公开草稿。验收声明是维护者对真实测试的记录，URL 校验不能替代实机验收。

## 当前交付验证边界

此工作流代码在 macOS 开发环境验证；没有在本次实现中启动 GitHub 发布，没有测试真实 Windows 安装/升级，也没有生成或替换生产签名密钥。Windows 原生验收仍是公开发布的阻断条件。
